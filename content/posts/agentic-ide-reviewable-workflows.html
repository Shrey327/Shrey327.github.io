An AI coding assistant can propose a change quickly. Checking that change still requires the source, the execution result and enough context to understand what happened. Agentic IDE brings those pieces into one workspace.

Agentic IDE is my local-first Theia/Electron workspace for Python AI engineering. It combines editing, terminals, model connections, RAG, training, evaluation and run traces. The current release is a 0.2.1 developer preview. This post focuses on the execution and review model rather than treating the feature list as a production-readiness claim.

Use a run as the common record

An experiment can begin in a template, a terminal-like workflow or a model evaluation panel. Its result should remain inspectable after navigating elsewhere. In the IDE, configured runs have history and trace actions. The local demo produces a nested trace through a managed OpenTelemetry Collector without requiring a model account.

The Python SDK exposes spans, metrics and evaluation events. LangChain and LangGraph integrations use a callback helper. Arbitrary projects are not silently instrumented. Existing code needs the relevant integration or explicit instrumentation before its internal steps appear in a trace.

That boundary is important. A launch record can establish that a command ran, but it cannot explain an uninstrumented function. The interface should not imply that it captured a complete account of execution simply because it can display a run.

Test model capabilities separately

Model connections support local services such as Ollama, LM Studio, vLLM and llama.cpp, plus HTTPS OpenAI-compatible endpoints. A connection has separate capability checks for chat, streaming, tool calls and embeddings.

A model that answers a chat prompt may still reject a tool schema or return malformed tool arguments. An embedding endpoint has a different contract again. Testing these capabilities independently lets a connection remain useful for the operations it actually supports.

Autonomous execution requires a successful tool-call check and the runtime selected by the sandbox policy. A chat-only connection can still answer questions or suggest patches. The workflow does not need to promote every connected model into an autonomous agent.

Stage edits before touching the project

Autonomous assistant sessions work on a staged source copy in a non-root Docker container. Host files stay unchanged until the user reviews the diff and applies it. Concurrent changes to the original source cause a conflict rather than silently overwriting newer work.

The container has resource and time limits, a read-only root filesystem and no general network access by default. Agent commands do not fall back to host execution if Docker is unavailable. Ordinary project runs and the editor terminal remain separate host-execution workflows.

This separation makes the authority of an action easier to understand. Inspecting a file, proposing a patch, executing a check and applying a patch are distinct operations. A successful check should be evidence for review, not permission for the agent to skip it.

There are still limits. Filename filters cannot detect every secret inside arbitrary source. Container isolation depends on the host and Docker daemon. Those constraints belong beside the workflow, not hidden behind a generic “safe” label.

Keep retrieval evidence close to the answer

The RAG workflow previews chunks before ingestion and records source, model and chunking provenance. Retrieval exposes scored chunks and metadata. Evaluation can use a JSONL dataset with exact or contains matching, with optional model-judge scoring kept separate.

This allows different failures to be investigated independently. A relevant document may never have been ingested. A chunk may be retrieved but lack the needed context. The answer model may receive the right context and still use it incorrectly. A single final score cannot explain which stage failed.

Runs and traces provide a shared place to inspect these operations. The goal is to make a failed case reproducible enough to investigate, then keep the case for the next comparison.

Choose what persists

Content capture and external telemetry export are off by default. Model credentials live in the operating system credential store. Project files retain connection identifiers and credential references rather than a plaintext fallback.

Telemetry settings do not mean every workflow is content-free. A RAG database needs document payloads. Evaluation cases and generation results have their own storage. The documentation distinguishes these paths so “content capture off” is not mistaken for a promise that no project content is stored anywhere.

A preview needs explicit boundaries

The repository documents implemented workflows and validation limits. The macOS build is an unsigned development build without notarization. The optional browser target is local development infrastructure, not a hosted multi-user service. Some serving engines have implemented launch paths without equivalent runtime validation.

I am treating this as a workspace for making AI engineering work inspectable: the proposed edit, the run, the evidence and the review decision. The README and implementation status describe how to try it and where the current boundaries are.
