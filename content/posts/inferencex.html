I built InferenceX one optimization at a time. The difficult part was deciding which measurements deserved to survive the experiment log.

InferenceX is a language model inference server written in PyTorch around a hand-written Qwen2.5-0.5B-Instruct forward pass. I used an RTX 4050 laptop GPU with 6 GB of memory under WSL2. A small model made it practical to test a change, inspect the result and try again without turning each experiment into an overnight job.

This article adapts my original benchmarking write-up. The measurements come from that write-up and the public repository. They have not been rerun for this site adaptation. [1]

The harness changed the first result

The first 37-token prompt took 333 ms to produce its first token. After warmup and a leading CUDA synchronization, the same no-cache model path took 39.9 ms. The difference came from initialization and timing boundaries. It was not a model optimization.

CUDA work is asynchronous. A timer started before earlier work finishes can charge that work to the operation being measured. The first forward pass also pays for initialization such as library handles and kernel loading. Those costs need their own accounting if the question is steady-state inference.

A short warmup still left the first timed run slower. I initially suspected cold matrix multiplication shapes. Warming the real shapes helped stability but did not explain the gap. Instrumenting the GPU showed memory clocks rising from 7001 MHz at idle to 8201 MHz under sustained load. Holding decode load for three seconds before timing addressed that effect.

Heat caused the opposite problem later. After about 20 minutes of tests, a path read 22.76 ms where an earlier result was around 18.6 ms. Repeating the measurement on an idle card removed the apparent regression. A fixed clock reading had not made the hardware state identical. These observations motivated alternating A/B arms within one process and keeping other timed jobs off the GPU.

A workload that could show the cache

My first KV-cache comparison reported a slowdown. The baseline was a lucky sample, individual timings varied widely and the prompt was too short to expose much repeated work.

A KV cache saves the keys and values already computed for the prefix. The next decode step computes projections for the new token while attention still reads the cached context. The attention work grows with context length. Caching does not make the entire decode step constant in context.

Reported controlled prompt sweep from the original experiment
Prompt tokensNo cacheKV cacheRatio
3735.0 tok/s39.1 tok/s1.12x
51223.4 tok/s45.0 tok/s1.92x
20482.5 tok/s38.7 tok/s15.5x

The larger contexts made the benefit visible. Cached latency was relatively flat over this measured range because other costs dominated. That is an observation about this workload and hardware, not an asymptotic claim.

The summary statistic mattered too. With only 63 inter-token observations, the harness’s p99 calculation selected the maximum sample. That offers little resolution into the tail. Outliers also pulled the mean enough to reverse the apparent direction of a change. I used repeated-run medians for the headline comparisons while keeping the raw variation relevant to any latency claim.

Estimate the size of the win

The naive cache appended with torch.cat. Replacing repeated allocation and copying with a pre-allocated buffer looked like an obvious speed improvement. Across three prompt lengths, its measured ratios were 1.09x, 0.97x and 0.96x. There was no convincing throughput gain.

At about 2035 context tokens, the history copy accounted for 23.8 MiB per decode step. Streaming model weights accounted for roughly 940 MiB. Removing a copy that represented about 2% of traffic was unlikely to stand out against the observed noise. Pre-allocation remained useful later because CUDA graph replay needs stable buffer addresses. Its value was not the speedup I had first expected.

The vocabulary projection offered a larger target during prefill. Generation needed the last position’s logits, yet lm_head projected every position into a vocabulary of 151,936 entries. At 2035 tokens, the write-up estimated about 554 GFLOP for the full projection. Slicing before it reduced the work to the row generation actually needed. The predicted saving was 24.8 ms. The measured saving was 25.1 ms with 529 MiB less peak memory.

Two batching experiments

Eight resident sequences reached 259.3 tok/s against 40.9 tok/s for serial service. I initially called the 6.34x ratio a continuous batching result. The workload generated 64 tokens per sequence with greedy decoding across eight requests. The harness used three rounds with alternating arm order. Equal-length requests arrived together into eight slots. It did not exercise replacement of completed requests.

To test scheduling, I used 32 requests through eight slots with output lengths drawn from a lognormal distribution. The lengths ranged from 8 to 271 tokens with a median of 66. In the static arm, a finished sequence’s slot stayed reserved until its group completed. The continuous arm could refill it.

Reported scheduling comparison with ragged outputs

Static110.7 tok/s3.29 of 8785

The 2.09x ratio answers the scheduling question for that ragged workload. It does not multiply with the earlier 6.34x result. Equal output lengths remove the opportunity this scheduling comparison was designed to measure.

Where the decode time went

A bandwidth estimate put batch-1 decode near a 6.5 ms floor for streaming weights. The measured step took 22 to 30 ms. Profiling a short-context step showed about 6.67 ms of GPU kernel work inside 22.80 ms of elapsed time, with 1023 launches per step. The gap pointed to work submission overhead.

Removing a per-step host synchronization helped by about 1.2x in the reported comparison. CUDA graphs addressed the repeated launch sequence itself. Persistent input buffers held changing token IDs, positions and context lengths. A fixed context bucket supplied stable shapes while device data determined which positions were live.

The graph harness reported 25.35 ms for eager decode with synchronization versus 8.65 ms for pipelined graph replay at batch 1 with a 37-token prompt. That is 39.4 to 115.7 tok/s, or 2.93x, within this harness. At batch 16 with the same short prompt, the separately reported ratio was 2.58x. These are graph-harness results rather than a general serving speedup.

The later fused paged Triton attention kernel removed the contiguous gather by reading the block table directly. Its reported long-context batch-16 comparison was 1.21x in wall time and about 1.4x in GPU time. The first profiler result had suggested 3.38x. An unchanged GEMM workload appeared to get dramatically faster between arms, which prompted a new interleaved profile. The result did not survive that check.

The decode deep dive follows the synchronization experiment, graph timing arms and fused kernel in more detail. [2]

Checks that exposed silent failures

Timing was only useful after the compared paths agreed on the result. Several failures returned plausible output or merely ran slower. A cache object was passed down but ignored by a decoder layer. An attention API call accepted a configuration but selected a slower backend. An additive mask did not stop non-finite values in unwritten cache memory from contaminating attention.

The checks needed to target those mechanisms. Prompt sweeps exposed repeated computation. Forcing each attention backend made unsupported fused paths explicit. Zero-initialized pools removed non-finite padding. Ragged lengths and a graph bucket crossing checked that replay used current positions without overwriting live history. Shuffled block tables kept a broken paged address calculation from passing by coincidence.

I describe those cases in the silent GPU failures article. The useful commonality is the check that made each failure observable. [3]

What is implemented

The public README distinguishes tested experimental components from the default serving path. CUDA graph decode is implemented but not wired into Engine. The fused Triton kernel is selected through an explicit mode switch. The paged-cache capacity result, 272,768 tokens versus 32,768 with per-slot reservations, measures capacity. It is not an 8.32x throughput claim. [4]

The habit I would keep is writing the prediction before the run. A result needs its mechanism, environment, workload, command and baseline. A failed prediction then has somewhere precise to send the next experiment.
