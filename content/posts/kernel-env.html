KernelEnv gives a model a PyTorch module and asks it to produce a faster GPU kernel. That makes the evaluator part of the learning problem.

I built the environment around compilation, numerical checks and timing on an H100. A submission could fail to compile, produce the wrong output or return a result that looked fast because the evaluator missed some work. Each case needed a different response.

This is an adaptation of my published KernelEnv article. Its later training and evaluation results are reported here as article evidence. They have not been independently rerun or reconciled with every release artifact for this adaptation. [1]

An episode and its reward

The environment selects a task from a pinned KernelBench revision. The model sees the reference module and the submission rules, then returns a ModelNew class whose forward path launches generated Triton kernels. A fresh worker runs static checks, compilation and numerical comparisons against the reference on five unseen random seeds. Only valid results reach timing.

Compile errors, mismatch statistics or timings go back to the model. The episode allows up to three attempts. The best attempt supplies the reward used by GRPO.

Invalid or incorrect submissions score zero. A correct submission starts at 0.25. The speed component uses the conservative lower bound of measured speedup:

reward = 0.25 + clip(log2(speedup_lower_bound), 0, 2)

A correct kernel that does not improve speed can still earn 0.25. A lower-bound speedup of 4x reaches the maximum reward of 2.25. The logarithm limits the influence of an extreme ratio on a group’s advantages. That reward is only meaningful if the evaluator measures the intended work.

What the evaluator has to exclude

The checks cover different ways a submission could violate the contract. Static inspection requires a Triton kernel and rejects prohibited framework shortcuts, imports and mutation of the judge. The reference is timed before importing the candidate so import-time behavior cannot quietly slow the baseline.

Fresh random inputs address cached outputs. Storage-alias checks and before-and-after input fingerprints address candidates that return an input or modify it. The worker writes its result through a designated result file rather than trusting candidate stdout. A separate process group and time limits contain hangs or crashes.

One deliberate adversarial test launched real work on a side CUDA stream without joining it. The profiler showed the extra stream but the environment still accepted the candidate. The one-stream rule existed yet did not fire on that path. Fixing the path and retaining the adversarial test mattered more than the presence of the rule in source.

The roofline supplied another sanity check. The implementation rejects reported times below 0.8 times its estimated hardware floor. That is an operational threshold based on a model of required bytes and FLOPs. Its assumptions must match the actual precision and work. A lower-precision computation can pass a loose numerical tolerance while using different hardware throughput, so a speed ratio alone does not establish better kernel design.

Timing as a learning signal

The initial timing setup had a reported standard deviation of 0.031 against a gap of 0.073 that the experiment needed to detect. Noise was large enough to influence which answer looked better within a group.

I captured the reference and candidate in CUDA graphs, then ran seven paired rounds with alternating order. A noise band derived from the interquartile range reduced the reward to a conservative speedup estimate. The reported noise fell to 0.0085. These figures describe the calibration in the original article; they are not a general accuracy guarantee for GPU timing.

Using the lower bound makes the reward harder to earn through a fortunate sample. It also makes uncertainty visible to the training setup. If a comparison is too noisy to distinguish the candidates, changing the policy optimizer does not fix that measurement.

When the contract was too strict

Some failures came from rejecting useful implementations. The first level-2 evaluation accepted zero of 48 answers. Those tasks combine a matrix multiplication or convolution with elementwise work. The rules had banned calls such as nn.Linear and nn.Conv* outright.

A revised hybrid contract allowed vendor matrix multiplication and convolution in host code under the stated precision restrictions while requiring the elementwise chain to use a generated kernel. The article reports that 29 of 35 previously rejected answers then passed. The evaluation question changed to match that contract. It should not be compared to a fully custom-kernel task without stating the difference.

Other fixes separated correctness from timing eligibility. A kernel that was correct but too slow to time could receive the correctness reward without a speed claim. A 20-second timing cap reduced how long slow candidates held the GPU lock. Moving large input fingerprints from CPU to GPU reduced validation overhead. Those were changes to the environment that made training practical.

The later experiment

The published article reports Qwen2.5-Coder-7B-Instruct with a 12-step SFT LoRA warm start on 28 verified level-1 teacher kernels. The later GRPO run used LoRA for 64 steps with eight generations per task. Its training setup lists 14 level-1 tasks plus 18 level-2 fusion tasks.

The comparison below uses an evaluation suite of 30 tasks with four samples per task, or 120 attempts for each model. The base, SFT and RL variants were evaluated with the same prompts and evaluator. The task groups and evaluation attempts must not be confused with the training inventory.

The reported aggregate RL correctness is higher, but every reported 95% bootstrap interval for the comparisons touches or crosses zero. This evaluation does not establish a statistically significant improvement. The held-out level-1 result remains zero for all three models. More samples or tasks could change the interpretation.

The article also reports a mean speedup of 1.64x for correct RL kernels on transfer tasks versus 1.30x for the base model. That is conditional on producing a correct kernel. It should be read alongside the low correctness rates rather than as the expected speedup for an arbitrary submitted task.

Keep the pilot separate

The older public release card describes a 16-step pilot with ten tasks. The later article reports the 64-step training run and 30-task evaluation above. Those are different experiments. Their step counts, task counts and aggregate outcomes are not interchangeable. [2]

The article’s strongest single-kernel example also came from an earlier pilot: a held-out GELU solved on a second attempt after a compile error, reported at 8.8x faster than eager PyTorch. Its explanation was fusion of an elementwise chain into one memory pass. That example does not summarize the later evaluation or establish transfer across the benchmark.

What remains uncertain

The original article identifies a remaining static-analysis gap: ordinary host-side tensor arithmetic such as x + y is not fully caught. The evaluator should be treated as a set of tested defenses with known limits. Numerical checks on fresh seeds are strong evidence for the tested inputs, but they are not a proof of correctness for every possible input.

The next useful evaluation would increase the samples per task and retain the full per-task distributions. It should preserve the run contract, precision rules and environment version. That would make it possible to distinguish a stronger policy from a change in which programs the judge accepts.
